# How ZDEW activates the FIPS provider

## Where the cryptography actually happens

ZDEW is three processes. Only one of them does network cryptography.

| Process | Crypto it performs | In scope for FIPS |
| --- | --- | --- |
| `ziti-edge-tunnel.exe` (service `ziti`) | All Ziti TLS, key generation, certificate handling | **Yes** |
| `ZitiUpdateService.exe` (service `ziti-monitor`) | Verifies Authenticode signatures on downloaded updates, HTTPS to the release stream | No. Uses Windows CryptoAPI and .NET, not OpenSSL |
| `ZitiDesktopEdge.exe` (tray UI) | None | No |

So the whole job is: make the OpenSSL that is compiled into `ziti-edge-tunnel.exe` load the validated provider.

## The mechanism ziti-edge-tunnel provides

As of **ziti-edge-tunnel v1.19.0** the Windows x86-64 build statically links **OpenSSL 3.6.3**, and the tunneler
resolves an OpenSSL configuration file at startup. From `programs/ziti-edge-tunnel/ziti-edge-tunnel.c`:

1. If `OPENSSL_CONF` is set in the environment, that path is used.
2. Otherwise it takes its own executable path (`uv_exepath`), replaces the file name with `openssl.cnf`, and uses
   that. In other words: **`openssl.cnf` sitting next to `ziti-edge-tunnel.exe`.**
3. The path is resolved with `uv_fs_realpath` and handed to `tlsuv_set_config_path`.
4. `tlsuv`'s OpenSSL engine then calls `OSSL_LIB_CTX_new` plus `OSSL_LIB_CTX_load_config(ctx, cnf)` and keeps that
   library context as the one all Ziti TLS runs in. If the config fails to load, it logs
   `failed to load config from [...]` and the engine is not configured.

Two consequences worth being explicit about:

- **No ziti-edge-tunnel changes are needed, and no environment variables are needed.** ZDEW has to put three
  files in the install directory and generate one of them at install time. That is the entire integration.
- The compiled-in `OPENSSLDIR` and `MODULESDIR` in the shipped binary are CI build paths
  (`D:/a/ziti-tunnel-sdk-c/...`) that do not exist on a customer machine. Nothing may depend on them, which is
  why the module path is written explicitly into `openssl.cnf`.

## Files ZDEW must place in the install directory

`APPDIR` is `C:\Program Files (x86)\NetFoundry Inc\Ziti Desktop Edge` by default. All three files go beside
`ziti-edge-tunnel.exe`.

| File | Origin | When |
| --- | --- | --- |
| `fips.dll` | Built per [build-fips-provider.md](build-fips-provider.md), Authenticode-signed with the ZDEW cert | Shipped in the MSI |
| `openssl.exe` | Same build | Shipped in the MSI |
| `openssl.cnf` | Written by an installer custom action, with `APPDIR` substituted in | Install time |
| `fipsmodule.cnf` | Generated by `openssl.exe fipsinstall` | Install time, on every machine |

`fipsmodule.cnf` holds an HMAC over the bytes of `fips.dll` plus the results of the power-on self-tests. It is
machine-specific and file-specific by design: that is the module's integrity check. Never ship a pre-generated
copy, and regenerate it whenever `fips.dll` changes.

**Ordering trap:** because the HMAC covers the file bytes, `fips.dll` must be Authenticode-signed *before*
`fipsinstall` runs. Signing at build time and generating the config at install time satisfies this. Signing a DLL
after generating its `fipsmodule.cnf` silently invalidates the integrity check, and the failure surfaces much
later as a provider activation error.

## The configuration we ship

```ini
openssl_conf = openssl_init

.include "C:/Program Files (x86)/NetFoundry Inc/Ziti Desktop Edge/fipsmodule.cnf"

[openssl_init]
providers = provider_sect
alg_section = algorithm_sect

[provider_sect]
base = base_sect
fips = fips_sect

[base_sect]
activate = 1

[fips_sect]
module = C:/Program Files (x86)/NetFoundry Inc/Ziti Desktop Edge/fips.dll

[algorithm_sect]
default_properties = fips=yes
```

Points that are load-bearing:

- **Forward slashes.** Write `APPDIR` with `/` separators. Backslashes in an OpenSSL config are escape characters.
- **`default` is absent.** Activating the default provider alongside FIPS leaves every non-approved algorithm
  reachable, which defeats the point. Only `base` (encoders, decoders, PEM handling -- no cryptography) and
  `fips` are activated.
- **`default_properties = fips=yes`.** This is what makes every algorithm fetch require a FIPS implementation, and
  it is also what `EVP_default_properties_is_fips_enabled` reports. Without it you have loaded the provider but
  not constrained anything.
- **`module` lives in `[fips_sect]`, the MAC values arrive via `.include`.** `fipsinstall` writes `[fips_sect]`
  containing `activate`, `module-mac`, `install-mac` and the self-test status. Our `[fips_sect]` adds only the
  module path, because `MODULESDIR` in the shipped binary is unusable. Do not restate `activate` in our block --
  duplicate keys in one section are order-dependent. Verify the merged result with
  `openssl.exe list -providers -config <path>`.
- A verification config that activates `default` and omits `default_properties` is fine for answering "does this
  DLL load", and wrong for shipping. Keep the two uses separate.

## Install-time command

```powershell
& "$APPDIR\openssl.exe" fipsinstall -pedantic `
    -out "$APPDIR\fipsmodule.cnf" `
    -module "$APPDIR\fips.dll"
```

`-pedantic` is not optional. §11.1 of the #4985 security policy documents `openssl fipsinstall -pedantic` as the
way to install the configuration to a non-default location, which is exactly what we are doing. It sets the
strictest FIPS-compliance options, which is also what §11.1(c) requires when it says the module's run-time
security checks *"shall not be disabled (by using OPENSSL_NO_FIPS_SECURITYCHECKS or any other method)"*.

Non-zero exit means the self-tests failed or the module could not be loaded. That must fail the install (or at
minimum refuse to write `openssl.cnf`), because an `openssl.cnf` that references a missing or unverified module
stops `ziti-edge-tunnel` from establishing TLS at all.

§11.1 also states that an authorized Crypto Officer performs these steps *"on each platform where it is intended
to be used"*, and that the generated config *"must not be manually modified without using the openssl fipsinstall
command"*. Running it from an elevated installer custom action on every machine satisfies both.

## Proving it at runtime

Both proofs are already built into ziti-edge-tunnel. No ZDEW code is required to obtain them.

**1. Startup log line.** The tunneler logs which config it used and how it found it:

```
	- openssl config   : configured using C:\Program Files (x86)\NetFoundry Inc\Ziti Desktop Edge\openssl.cnf found by default location
```

`found by` is either `default location` (next to the exe) or `environment variable` (`OPENSSL_CONF`). If the line
is absent, no config was loaded and the tunneler is running on OpenSSL's built-in implementations.

**2. Version output.** `tlsuv` appends `[FIPS]` to its reported TLS library version when
`EVP_default_properties_is_fips_enabled` is true for the configured library context:

```
> ziti-edge-tunnel.exe version -v
...
tlsuv:  v0.44.0[OpenSSL 3.6.3 9 Jun 2026 [FIPS]]
```

`Installer\build.ps1` already captures `ziti-edge-tunnel.exe version -v` into the build log, so the same string is
what ZDEW should surface in the UI.

The earlier attempt at this feature showed the FIPS panel based on `File.Exists("fips.dll")`, which proves only
that a file was copied. Replace that with the real state, read from the tunneler.

## Things outside the OpenSSL module boundary

Be precise about these when answering a compliance questionnaire. A claim that overreaches is worse than a
narrow one.

**Ziti end-to-end encryption.** `ziti-sdk-c` ships four E2EE implementations
(`library/e2ee/e2ee_libsodium.c`, `e2ee_aes_gcm_wincrypto.c`, `e2ee_tls.c`, `e2ee_none.c`) and negotiates a mode
with the peer:

| Mode | Implementation on Windows | FIPS position |
| --- | --- | --- |
| libsodium | XChaCha20-Poly1305 secretstream | Not an approved algorithm. Outside any validated module |
| aes-gcm | Windows CNG / BCrypt | Approved. Covered by Microsoft's own CMVP certificates, not by #4985 |
| tls | OpenSSL, so the FIPS provider | Approved, and inside our module boundary |
| none | -- | No E2EE |

`e2ee_tls` was added in ziti-sdk-c 1.19.0. For a FIPS claim that covers E2EE payloads and not merely the
transport, the mode has to be constrained to `tls` (or `aes-gcm`, with Microsoft's certificate cited instead of
OpenSSL's) on both ends. That is a network-policy decision, not an installer setting, and it needs confirming
with the SDK maintainers -- see the open questions in [implementation-plan.md](implementation-plan.md).

**Update verification.** `ziti-monitor` checks Authenticode signatures and talks HTTPS to the release stream
using Windows CryptoAPI and .NET Framework, both of which use Microsoft's validated modules when the machine has
the Windows FIPS policy enabled. Not covered by #4985.

**Windows FIPS mode.** The Windows "use FIPS compliant algorithms" security policy is independent of everything
here. It constrains CNG consumers. It does not affect OpenSSL, and OpenSSL's FIPS provider does not require it.
Some customers will nonetheless expect it on; enabling it is their configuration decision and costs us nothing.

## The win32crypto variant

The alternate distribution exists because the Windows tunneler used to offer a Windows-crypto TLS backend
alongside OpenSSL. ZDEW carries that through as the `-win32crypto` twins of every release stream, promoted in
lockstep.

Upstream has **not** dropped it as of ziti-edge-tunnel v1.19.0: the release still publishes
`ziti-edge-tunnel-Windows_x86_64-win32crypto.zip`. Confirm the retirement plan with the tunneler maintainers
before removing the twin streams from ZDEW; the FIPS work does not depend on that removal either way. Note that
if the twin does survive, only the OpenSSL build can load the FIPS provider, so a `-win32crypto` build must never
be shipped with FIPS enabled.
